## Problem Statement

People learning offensive security on a Raspberry Pi have two bad options. Kali
Linux is powerful but utilitarian and intimidating — a wall of terminals that
assumes you already know what you're doing. Raspberry Pi OS is friendly but has
no security focus. Nobody has built the box a *student* of offensive security
would actually want to live in: beautiful, discoverable, and teaching, without
dumbing down the real tools.

AETHER OS is that box — a macOS-grade desktop fused with a serious ARM64 pentest
toolkit, aimed at students and CTF players, distributed as a flashable open-source
image.

## What Makes This Cool

The "whoa" is **"a hacker OS that doesn't look like 2009."** The fusion of a
genuinely premium desktop with real security tooling is the identity and the
moat — not any single tool.

The signature feature is **Lab Mode**: a single toggle that cinematically *arms*
the box. Everyday profile → Security Research profile with a visible transition,
the toolkit lights up in the dock, a scope/target banner appears, the firewall
profile switches, and the legal-authorization gate is part of the drama rather
than a nag. Disarm, and you're back to a clean daily driver. That one switch is
the demo and the screenshot in a single gesture.

Supporting delights: tools launched from a beautiful dock with results in real
UIs (terminal still there for pros), a Security Center "cockpit" that honestly
shows the box's own posture *and* the current engagement scope, and
screenshot→annotate→findings-log report capture baked into the desktop so a CTF
writes itself as you go.

## Constraints

- Target: Raspberry Pi 4 Model B (BCM2711, ARM64, VideoCore VI), 2/4/8 GB tiers.
- Solo open-source project. Real users must be able to download and run it.
- VideoCore VI GPU: V3D/Mesa (GLES/Vulkan). QML performance on this GPU is an
  unverified assumption and the main technical risk.
- No proprietary Apple assets, logos, or SF Symbols. 100% original branding.

## Premises (all accepted by the owner)

1. **The differentiator is the experience, not the tools.** Every tool is an
   existing ARM64 `apt`/Flatpak package. AETHER never out-tools Kali and won't
   try. Value = desktop, Lab Mode, discoverability, teaching.
2. **No custom OS and no custom compositor.** Build a desktop shell + tooling
   layer on an existing base (Raspberry Pi OS 64-bit or Debian ARM64) and an
   existing Wayland compositor (labwc/wayfire). Writing a compositor would kill
   the project.
3. **v0.1 is tiny.** Polished shell + Lab Mode + ~8 hand-picked tools + one
   killer demo. NOT the 14-category toolkit, forensics tiers, LUKS, or the
   update manager. Those are earned later.
4. **No distribution = no project.** For open source: a `.img.xz` on GitHub
   Releases, flashable in Raspberry Pi Imager, with SHA256 + signature. Tweet →
   booted in 15 minutes or adoption is zero.
5. **"Beautiful" is the actual risk, not the tools.** A janky macOS knockoff
   looks worse than Kali and kills the premise. The non-negotiable hard work is
   nailing the shell visuals.

## Approaches Considered

### Approach A: Reskin + Lab Mode layer (minimal viable) — CHOSEN
Raspberry Pi OS + labwc dressed with existing components (waybar, nwg-dock, GTK
theme) plus a small Python/GTK control panel for Lab Mode. Fastest to a bootable,
demoable, flashable image with the lowest stall risk. Trade-off: "premium" is
capped by GTK theming and must be checked against the beauty bar (premise 5) on
real hardware; surfaces that fall short get a targeted Qt/QML rebuild.

### Approach B: Custom Qt6/QML shell over labwc (ideal architecture) — upgrade path
Keep labwc as compositor (premise 2); write the top bar, dock, launcher, and Lab
Mode control center as one cohesive Qt6/QML app via layer-shell-qt. Full control
of the look and the Lab Mode transition. Highest ceiling; highest risk (QML perf
on VideoCore VI, large surface, stall risk). Not the v0.1 plan — held as the
targeted technique for any single surface where GTK theming can't clear the bar.

### Approach C: Vertical slice — ship the demo first (creative/lateral) — folded in
Build the Lab Mode demo before the OS, prove the beauty bar and the distribution
loop at minimum surface, then grow. Not chosen as the headline, but its
sequencing discipline is adopted inside B below.

## Recommended Approach

**Approach A (reskin + Lab Mode layer).** Raspberry Pi OS 64-bit + labwc,
dressed with existing, battle-tested components (waybar/wf-shell top bar,
nwg-dock, a GTK theme, a custom icon set). Lab Mode is a small Python/GTK
control panel plus scripts that flip the profile, tool group, firewall, and
scope banner. Almost no new UI code. Chosen for the fastest path to a bootable,
demoable, flashable image with the lowest stall risk — you assemble and theme
proven pieces instead of writing a shell from scratch.

The honest trade-off (premise 5): "premium" is capped by what GTK theming can
do. If the themed desktop looks like a knockoff, the "beautiful pentest box"
identity weakens. So A is run with one explicit discipline:

- **Beauty gate, early and on real hardware.** Before building out breadth, get
  the themed desktop + dock + top bar onto a real Pi 4 and judge honestly: does a
  screenshot make someone say "that's a Raspberry Pi?" If yes, press on. If the
  GTK ceiling is clearly too low for a given surface, selectively rebuild *only
  that surface* in Qt6/QML (the Approach B technique) — but only where theming
  demonstrably failed, never as a default.
- **Lab Mode is the star, built first.** The Python/GTK Lab Mode control panel +
  the arm/disarm transition (profile, tool group, firewall, scope banner) is the
  first real feature, because it's the demo and the identity.
- **Always-bootable, scope stays premise-3 tiny.** Every milestone produces a
  flashable image. v0.1 = themed desktop + Lab Mode + dock + ~8 tools + report
  capture. Everything else is post-v0.1.
- **Lab Mode privilege boundary (eng review decision).** Arming flips the
  firewall and service state — root operations. The unprivileged GTK panel must
  NOT run sudo or interpolate strings into a shell. v0.1 uses **pkexec on fixed,
  argument-free scripts** behind a locked Polkit policy: a real privilege
  boundary without building the full typed helper yet. Upgrade to a
  narrowly-scoped Polkit + typed/JSON-allowlist helper when the tool/service
  matrix grows or per-action auth is needed.
- **The arm/disarm transition is an app-level animation**, inside the GTK/Qt
  panel — not a compositor effect. This keeps it working on labwc (which is
  animation-light) and makes the labwc-vs-wayfire choice non-blocking.

Approach B (custom Qt6/QML shell) is retained as the targeted upgrade path for
any single surface where GTK theming can't clear the bar — not the v0.1 plan.

## Open Questions

- **Base: Raspberry Pi OS 64-bit vs Debian ARM64?** Pi OS gives the best
  hardware/firmware support out of the box (recommended default); Debian is
  cleaner but more hardware integration work. Decide before the first image.
- **Compositor: labwc vs wayfire?** Largely de-risked by making the transition
  an app-level animation (above). labwc is lighter and config-driven (default
  for A); pick it unless something else needs wayfire's compositor effects.
- **Can GTK theming clear the premium bar? (the central risk for A.)** Unverified
  until the beauty gate runs on real hardware. If it can't on a given surface,
  that surface is a candidate Qt/QML rebuild (Approach B technique), scoped to
  just that surface.
- **Tool rendering depth.** How many of the 8 tools get a real UI vs a styled
  terminal launch in v0.1? Likely 1-2 real UIs max for v0.1.
- **Does the image ship tools preinstalled, or install-on-first-Lab-Mode?**
  Affects image size and the premise-4 download experience.

## Success Criteria

- A `.img.xz` on GitHub Releases that flashes via Raspberry Pi Imager, boots on
  a Pi 4, and reaches the desktop.
- The Lab Mode arm/disarm transition runs at a convincingly smooth frame rate at
  1080p on real hardware.
- A 60-second video demo that makes a security student say "wait, that's a
  Raspberry Pi?"
- ~8 real pentest tools launchable from the dock; at least one with a non-terminal
  results UI.
- Report capture: screenshot → annotate → appended to a findings log.
- First external person flashes it and boots it successfully from the README alone.

## Distribution Plan

- **Artifact:** `aether-os-vX.Y.Z-arm64.img.xz` + `.sha256` + detached signature.
- **Channel:** GitHub Releases, README with Raspberry Pi Imager instructions.
- **Build:** customized `pi-gen` stage(s) producing the image reproducibly.
- **CI/CD:** GitHub Actions on tag → build image on an ARM64 runner (or
  cross/qemu) → checksum + sign → attach to the Release. Manual trigger is fine
  for v0.1; automate on tag once the build is stable.
- **No secrets or signing keys in the repo or image** (premise consistent with
  the spec's security mandates).

## Build status (2026-10-16)

v0.1 **builds**: a genuine arm64 `.img.xz` was produced by pi-gen under qemu
emulation in a Docker container, with all AETHER packages present and zero armhf
packages. Boot on real Pi 4 hardware is still unverified.

**Decision (supersedes the base-OS choice): Debian trixie, not bookworm.** pi-gen's
`arm64` branch targets trixie; its `bookworm` branch is 32-bit armhf only, so there
is no clean bookworm-arm64 path. Trixie (Debian 13) is current and also carries
`swappy` + `fonts-jetbrains-mono`. The build host must match (`debian:trixie`).

Local Windows build notes (all handled in `build/build.sh` / the container flow):
pi-gen needs LF line endings (git `autocrlf` breaks it), `qemu-user-static` +
binfmt registration for arm64 emulation, and `debian-archive-keyring`. The GitHub
Actions path on a native arm64 runner avoids the qemu/emulation steps entirely.

## Engineering Review (plan-eng-review, 2026-10-16)

Target: this design doc. Greenfield plan — findings are architecture,
feasibility, and sequencing, not code defects. Scope accepted as-is.

### Findings & dispositions

- `[P1] (8/10)` Lab Mode privilege boundary was undefined. **Resolved (D1):**
  v0.1 uses pkexec on fixed, argument-free scripts behind a locked Polkit
  policy; no GUI-as-root, no shell interpolation. Upgrade path: typed
  Polkit helper. — *accepted*
- `[P2] (8/10)` "Cinematic transition" risked depending on a compositor labwc
  can't drive. **Resolved:** transition is an app-level animation in the panel;
  compositor choice is now non-blocking. — *accepted*
- `[P2] (7/10)` pi-gen ARM64 build in CI needs loop devices + privileged
  container + binfmt/qemu or a native arm64 runner; x86 GitHub runners won't
  work unmodified. — *accepted (budgeted in Distribution Plan)*
- `[P2] (6/10)` 2GB idle RAM budget (<650MB) is tight; the "Visual" animation
  profile likely exceeds it on 2GB. **Resolved:** default animation profile is
  tied to RAM tier; measure idle RAM on a real 2GB board. — *accepted*
- Code quality: keep the privileged helper tiny — fixed argument arrays,
  allowlist, no shell interpolation. — *accepted*

### Tests this plan must protect (no code yet)

- **CRITICAL (regression):** disarm fully reverts the nftables ruleset applied by
  arm. A firewall that doesn't revert is worse than none.
- The privileged scripts reject/!execute anything outside the pkexec policy.
- Report capture appends to the findings log.
- Image boots to desktop on real Pi 4 hardware (manual, per milestone).

### NOT in scope (deferred)

- Full typed Polkit helper daemon — deferred until the tool/service matrix grows.
- 14-category toolkit, forensics tiers, LUKS, update/recovery manager, Security
  Center cockpit — all post-v0.1 per premise 3.
- Custom Qt/QML shell — per-surface upgrade path only, not v0.1.

### What already exists (reuse, don't build)

- Base/compositor/panel/dock: Raspberry Pi OS 64-bit, labwc, waybar, nwg-dock.
- Privilege boundary: Polkit/pkexec (don't hand-roll privilege escalation).
- Firewall: nftables atomic ruleset swap (don't script iptables by hand).
- Tools: existing ARM64 apt/Flatpak packages. Image build: pi-gen.

### Failure modes

- **Arm succeeds, disarm fails to revert firewall** → box left in an exposed or
  wrong state silently. Mitigation: disarm revert is regression-tested; consider
  an atomic apply with a rollback timer. **Critical gap until tested.**
- pkexec policy too broad → privilege-escalation surface. Mitigation: fixed
  scripts, no arguments, reviewed policy.
- CI image build flaky → no releases. Mitigation: pin the build action; document
  a local `pi-gen` fallback.

### Parallelization

| Step | Modules | Depends on |
|------|---------|-----------|
| pi-gen bootable base | build/ | — |
| Theme + dock + top bar | desktop theming | base |
| Lab Mode panel + pkexec scripts | lab-mode/ | base |
| Report capture + tools | tools/ | base |

Lane A: base → theming. Lane B: Lab Mode (after base). Lanes A and B can run in
parallel once the base image boots; tools/report capture join last. Small solo
project — coordination cost is low.

| Token | Value |

- **Type:** Inter (UI/body, explicitly assigned for this Operate surface),
  JetBrains Mono (terminal/data/tabular numerals). Scale: Display 24 / Heading 18
  / Body 14 / Label 12 / Mono 13. Body ≥14px, AA contrast (palette clears 4.5:1).
- **Spacing:** 4px base — 4/8/12/16/24/32. **Radii:** 6 (controls) / 10 (cards) /
  0 (top bar). **Elevation:** offset+blur shadows only, never a zero-offset halo.
- **Theme the browser/GTK surfaces** from the palette: selection, caret, scrollbars,
  focus rings, underline offset. (The cheapest "designed, not assembled" tell.)

### Information architecture (Pass 1)

Persistent hierarchy on the armed desktop: (1) **Lab Mode state** — a permanent
top-bar indicator; the user must always know armed vs safe. (2) Active tool/
terminal window. (3) Dock + top bar (ambient). Nothing competes with the mode
indicator.

### Lab Mode transition (Pass 3)

App-level animation (not a compositor effect), ~280ms ease-out
`cubic-bezier(0.16, 1, 0.3, 1)`, honors reduced-motion (Performance profile →
instant):

- **Arm:** scope banner slides down from under the top bar (translateY + fade);
  dock tools stagger-fade in (~30ms each); top-bar badge flips Safe → **ARMED**;
  firewall indicator shows "applying…" then ✓.
- **Disarm:** reverse.
- **Arm-fail:** badge returns to Safe + an error toast. **Never render ARMED
  unless the firewall actually applied** (ties to the eng review's firewall-revert
  regression).

### Interaction states (Pass 2)

| Feature | Loading | Empty | Error | Success | Partial |
|---|---|---|---|---|---|
| Lab Mode toggle | "applying…" on firewall indicator | n/a | arm-fail toast, badge stays Safe | ARMED badge + banner | n/a |
| Tool launch | spinner on dock icon | n/a | "couldn't launch X" toast | window opens, dock running dot | n/a |
| Security Center | per-check spinner | "Not Configured" card w/ action | "Check Failed" + reason + retry | "Protected" + timestamp+source | "Attention"/"Unknown"/"Unsupported" states |
| Findings log | — | warm empty: "No findings yet — screenshots you capture land here" + capture hint | write-fail toast | entry appended | — |

Security Center uses the honest state set: Protected / Attention / Not Configured
/ Unsupported / Unknown / Check Failed — each with timestamp, source, and a
remediation action. No security theater.

### Responsive & accessibility (Pass 6)

- **Keyboard:** full shell navigation (launcher, dock, top bar, Lab Mode) — it's
  an OS; keyboard-only must work. 2px accent focus rings everywhere.
- **Touch:** 44px minimum targets (DSI/USB touchscreens).
- **Contrast:** WCAG AA on the dark theme; provide the High-Contrast token set.
- **Non-color status:** Lab Mode armed and every Security Center state carry a
  text/icon label, never color alone (colorblind users).
- **Reduced motion:** the Performance animation profile disables transitions.
- **Displays:** top-bar right cluster collapses to an overflow at 720p/narrow;
  dock auto-hides on small displays; top bar adapts under fullscreen apps.
